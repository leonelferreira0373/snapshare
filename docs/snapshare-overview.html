This document describes SnapShare as deployed at https://snapshare-share.vercel.app on the date of issue. The underlying source code is open and tracked at https://github.com/leonelferreira0373/snapshare.

1. Executive Summary

SnapShare is a free, browser-based, peer-to-peer file transfer service. Two devices open the same URL; one shows a QR code or a six-character pairing code; the other scans or types it; the connection is established. Files then flow directly between the two devices, encrypted end-to-end, without ever passing through a SnapShare server.

There are no accounts. There is no upload limit. There is no quality loss. There is no recurring cost — for the operator or for the user. The service is hosted on a free Vercel static plan, relies on the public PeerJS signaling broker for the brief handshake, and is otherwise fully autonomous.

The product is multi-device, multi-platform, and multi-language (Portuguese and English, with Portuguese as the default). It includes light and dark theming, an installable Progressive Web App (PWA), drag-and-drop anywhere on a desktop screen, in-app QR scanning via camera or screen capture, automatic clipboard capture (text and images), tap-to-copy on received text payloads, file-type-aware iconography, resend, cancel, and per-peer disconnect.

One-sentence pitch The fastest, most private way to move a file from one device to another, with nothing installed, no account created, and no third party touching the bytes.

3. How It Works

SnapShare is a single-page application written in TypeScript and React, bundled with Vite, and hosted as a fully static deployment on Vercel. All runtime logic executes inside the user's browser; the SnapShare backend consists of zero servers under operator control.

3.1 Connection establishment

  1. Page load. The browser registers a unique peer identifier with the PeerJS public broker over a brief WebSocket handshake. Identifiers are six alphanumeric characters, persisted in localStorage so they remain stable across visits.
  2. Discovery. Device A displays a QR code containing the URL with its peer identifier. Device B opens the same URL (typically by scanning the QR with the OS camera, or by typing the six-character code).
  3. Handshake. Device B asks the broker to connect to Device A's identifier. The broker relays the WebRTC offer/answer between the two devices — a few kilobytes total. ICE candidates are exchanged using free public STUN servers (Google).
  4. Data channel. A reliable WebRTC DataChannel opens directly between the two devices. From this point onwards, the broker is idle; files flow peer-to-peer.

          |                                         |
          |   1. Register identifier (broker)       |

3.2 File transfer protocol

A file transfer is initiated by sending a meta JSON message containing a generated transfer identifier, the original filename, the declared MIME type, and the total byte length. The sender then streams the file in sixteen-kilobyte binary chunks. Backpressure is governed by the underlying RTCDataChannel: when the buffered amount exceeds sixteen megabytes the loop awaits the bufferedamountlow event before resuming. A terminating eof message closes the transfer; the receiver reassembles a Blob and either triggers an automatic download (binary) or activates tap-to-copy (text).

A complementary cancel message exists for either side to abort an in-flight transfer cleanly. A hello message exchanged on connection open carries platform metadata used for the friendly device labels.

4. Privacy & Security

4.1 What never leaves the two devices

The contents of every file you transfer remain between the sending device and the receiving device. They are not uploaded to any server, do not pass through any cloud storage bucket, are never logged, and cannot be reviewed by the operator. There is no backend that could be subpoenaed or breached, because there is no backend that ever sees the payload.

4.2 What does briefly traverse the broker

To establish the peer-to-peer link, two short JSON messages — the WebRTC offer and answer — must be relayed between the two devices. These contain cryptographic fingerprints and network address candidates. They do not contain any user content. Once the link is open, the broker is no longer in the loop.

4.3 Encryption

WebRTC DataChannel connections are encrypted at the transport layer using DTLS 1.2 or later. The session keys are negotiated directly between the two devices. SnapShare does not implement an additional application-level cipher; it relies on the standardised, browser- enforced WebRTC security model, which is end-to-end by construction.

4.4 Data retention

SnapShare collects no analytics, sets no first-party tracking cookies, and does not store user data. The only persistent state is on the user's own device, in localStorage, and is limited to: the selected language, the chosen theme, the persistent peer identifier, the list of recently paired devices (up to eight), the clipboard-capture toggle state, and the keep-awake toggle state. The user may clear this state at any time through normal browser controls.

5. Limitations & Honest Caveats

5.1 Network reach

Two devices on the same local network connect with one hundred percent reliability. Across different networks the success rate is roughly ninety to ninety-five percent, dependent on the NAT type at each end. The remaining cases — typically carrier-grade symmetric NAT combined with restrictive corporate firewalls — require a TURN relay, which SnapShare does not currently provision (paid bandwidth). When a connection cannot be established, the device shows a clear error rather than retrying silently.

5.2 Mobile background behaviour

Mobile browsers suspend the JavaScript engine and tear down WebRTC connections when a tab loses foreground status. There is no portable browser-side mechanism to keep a peer connection alive in true background. SnapShare offers the Keep screen awake toggle, which holds a screen Wake Lock and keeps the tab considered visible while the screen is on; this is the maximum that can be achieved without a native application wrapper.

5.3 File size

Received files are assembled in browser memory before being saved. Files above approximately five hundred megabytes are reliable on desktop browsers; on mobile, memory pressure may cause the tab to be killed. A streaming save-to-disk path using the File System Access API is on the roadmap but requires Chromium-class browsers.

5.4 Clipboard reach

Web browsers expose images and text from the system clipboard reliably. They do not expose arbitrary file types copied from the OS file manager. A video or document copied from Windows Explorer into the clipboard cannot be read by a web page; only its filename appears. For such payloads users should rely on drag-and-drop or the Add files button.

5.5 iOS download path

On iOS Safari, downloads land in the system Files application rather than the Photos library. Users may save received images to Photos manually from within Files. This is a platform limitation.

6. Quick Start Guide

  1. Open the service. Both devices visit https://snapshare-share.vercel.app. The first visit on a device generates and remembers a six-character pairing code.
  2. Pair. On Device A, expand the QR code (chevron button beside the code). On Device B, scan it with the OS camera or the in-app scanner. Alternatively, type Device A's six-character code into Device B's pairing field — auto-capitalised and auto-hyphenated as you type.
  3. Confirm. Both devices show Paired devices (1) with a green dot beside the partner's name.
  4. Send. Drag a file onto the drop zone (or anywhere on the desktop page), tap Add files, paste with Ctrl+V, or — if the clipboard toggle is on — simply copy on your other application and return to the SnapShare tab.
  5. Receive. The other side shows the incoming row with a live progress bar. On completion, the file downloads automatically; for text payloads, the row becomes tap-to-copy.
  6. Resend or cancel. Completed sender rows offer Reenviar. In-progress rows offer the cancel cross. Either side may cancel; both sides observe the cancellation cleanly.
